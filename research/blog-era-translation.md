# Then → Now: translating a kubernetes.io blog post to the pin

Resolves issue #54 (`k3ii/k8s-academy`), sub-issue of the MAP issue #52
([Blogwalk](https://github.com/k3ii/k8s-academy/issues/52)).

**Research date:** 2026-08-27. **The pin:** `kubernetes/website@7c76070faf9b19e6a417c446043dbafd10a7aa1d`
(2026-08-26). The newest Kubernetes at the pin is **v1.37 "Garhwal"**, released 2026-08-26 —
the pin date itself.

## What this is for

Every `blogwalk/` exercise file has a section called **"The diff, and why"**. This document is
its input. The blogwalk stance is that a stale post's *staleness is the lesson*: a post that
still works teaches you its own era, and a post that broke teaches you what changed and why.
That only holds if the *why* is right, so this is the table the authoring tickets read instead
of each re-deriving eleven years of release history and each getting it slightly differently.

Every row is shaped the same way:

| What the post says | What is true at the pin | Changed in | The decision behind it |

The fourth column is the one that matters. "It was replaced" is not an answer; the sentence has
to name the pressure that moved it.

## Read this before trusting any release number, including the ones here

**Kubernetes' own CHANGELOGs and deprecation announcements misstate their own removals, in both
directions.** This was not a hypothesis going in — all three lines of research hit it
independently, and it is the single most important methodological finding in this document:

- **`CHANGELOG-1.28` announces the `azureFile` in-tree plugin removal.** That commit was
  reverted; the code is demonstrably present on `release-1.28` and `release-1.29`. Real removal
  was **v1.30**.
- **`kubectl run-container`'s removal was announced in v1.8.** A bad conflict resolution in
  PR #50998 reinstated the alias two days later. It actually died in **v1.13**.
- **The dockershim removal was announced in the v1.20 blog as "currently planned for the 1.22
  release".** It landed in **v1.24** (May 2022). Nearly every 2021 post carries 1.22 in good
  faith.
- **`--export` was announced for v1.18, removed in v1.19. `kubectl convert` was announced for
  v1.17, removed in v1.20** — and was deprecated in v1.13, not the v1.14 the deprecation tables
  claim.

So a deprecation notice tells you the *intent* of a release, never the fact. Every removal
claim below was confirmed by reading the **source tree at the release tag** (`gh api
repos/kubernetes/kubernetes/contents/...?ref=<tag>`), not by trusting the note that announced
it. Authoring tickets should hold themselves to the same standard, and this is worth stating in
the exercise files themselves: *the announcement is not the event.*

This is the same failure mode [`strands/source-archaeology.md`](../strands/source-archaeology.md)
describes for file paths — accurate when published, which is exactly why it is convincing now —
one level up, at the level of the changelog.

## Confidence and gaps

**198 rows across 14 tables. 192 fully verified** against a primary source carrying a release
number. **6 rows carry an inline `[UNVERIFIED]` marker**, and four further gaps are named in the
Traps prose of the part that found them. Nothing here is quoted from memory; where a release
number could not be confirmed it is marked rather than guessed, because a wrong version number
is worse than an admitted gap — it gets copied into an exercise file and read as fact.

Known gaps worth naming up front, so no authoring ticket rediscovers them:

- **Bootstrap-token GA release** — unconfirmed; CHANGELOGs 1.6→1.34 carry no promotion note.
  Last confirmed status is beta in v1.8.
- **kubenet's removal release** — no CHANGELOG names it. v1.24 is inferred structurally
  (the package exists at `v1.23.0`, 404s at `v1.24.0`).
- **FlexVolume has no removal release** — it is still compiled in and registered at v1.37.
  That row asserts an absence, not a number.
- **`resource.k8s.io/v1beta1`'s claimed v1.36 removal** — no changelog confirms it.
- **The ScheduledJob → CronJob rename rationale** — no primary source states it. The releases
  are verified; the *why* is not.
- **v1.36 claims** rest on `CHANGELOG-1.36` plus a `release-1.35`↔`release-1.36` tree diff;
  the v1.36 blog posts fetched truncated.

## The three traps most likely to ruin a lab

Pulled forward out of the per-part Traps sections because each one *silently succeeds*:

1. **`--authorization-mode` still defaults to `AlwaysAllow` at v1.37.** The kube-apiserver
   reference says so verbatim. The 2015 posts are *correct about the binary* — only kubeadm
   saves you. Any exercise that starts a raw apiserver must pass `--authorization-mode=Node,RBAC`
   explicitly, or it teaches a cluster with no authorization at all and looks like it worked.
2. **The API still accepts every dead volume type.** `core/v1` at `release-1.37` still declares
   `gcePersistentDisk`, `rbd`, `glusterfs`, `gitRepo` and a dozen more. A 2015 manifest applies,
   the PV is created, the Pod is admitted *and scheduled* — and fails at mount time on a node,
   minutes later, somewhere the reader isn't looking.
3. **`kubectl apply` is still client-side by default at v1.37.** Server-side apply is GA since
   v1.22 and its feature gate was deleted in v1.32, which reads like "it won" — but
   `--server-side` defaults to `false` and the `last-applied-configuration` annotation a 2016
   post describes is still being written to your objects today. Here the *old* post is more
   accurate than a 2021 one.

### API surface

#### The v1beta1 / v1beta2 / v1beta3 era and the move to core `v1`

| What the post says | What is true at the pin | Changed in | The decision behind it |
|---|---|---|---|
| `apiVersion: v1beta1` (or `v1beta2`) with `id`, `desiredState`, `currentState`, `/minions`, `labels=` query param | Nothing serves these. Core objects are `apiVersion: v1`; `id`→`metadata.name`, `desiredState`→`spec`, `currentState`→`status`, `/minions`→`/nodes`, `labels=`→`labelSelector=`, `fields=`→`fieldSelector=` | **v1beta1 and v1beta2 were deleted 2015-06-01** — [PR #8917 "Delete deprecated apis"](https://github.com/kubernetes/kubernetes/pull/8917), listed in the [v0.19.0 release notes](https://github.com/kubernetes/kubernetes/releases/tag/v0.19.0). Date stated in [docs/api.md @ v1.0.0](https://github.com/kubernetes/kubernetes/blob/v1.0.0/docs/api.md): "The v1beta1 and v1beta2 APIs were deleted on June 1, 2015." | v1beta1/2 had no `spec`/`status` split: desired and observed state were intermingled in one flat object, so the reconciliation contract that the whole control plane is built on was not expressible in the wire format. v1beta3 restructured every object around `metadata`/`spec`/`status` so that "what I asked for" and "what is" are separately readable and separately writable. |
| `apiVersion: v1beta3` — Pods/RCs/Services with `spec`/`status`, `service.spec.portalIP`, `pod.spec.host`, `createExternalLoadBalancer` | `apiVersion: v1`. `portalIP`→`clusterIP`, `pod.spec.host`→`pod.spec.nodeName`, `createExternalLoadBalancer: true`→`spec.type: LoadBalancer`, `publicIPs`→`spec.type: NodePort`, `containers[*].privileged`/`capabilities` moved under `containers[*].securityContext`, `state.termination`→`state.terminated`, `pod.status.Condition`→`pod.status.conditions` | v1beta3 was **enabled and made the default API version in v0.15.0** ([PR #6098](https://github.com/kubernetes/kubernetes/pull/6098), in the [v0.15.0 notes](https://github.com/kubernetes/kubernetes/releases/tag/v0.15.0)). `v1` was created **in v0.16.0** by literally cloning v1beta3 ([PR #7454 "Cloning v1beta3 as v1 and exposing it in the apiserver"](https://github.com/kubernetes/kubernetes/pull/7454)). `v1` **enabled by default 2015-06-04, v0.19.0** ([PR #9269 "Make v1 enabled by default"](https://github.com/kubernetes/kubernetes/pull/9269)). **v1.0.0 stopped exposing v1beta3 by default** ([PR #10525](https://github.com/kubernetes/kubernetes/pull/10525), in the [v1.0.0 notes](https://github.com/kubernetes/kubernetes/releases/tag/v1.0.0)); the code was deleted in the **v1.1** cycle ([commit `1c3233a` "Remove v1beta3", 2015-07-23](https://github.com/kubernetes/kubernetes/commit/1c3233a1), confirmed an ancestor of `v1.1.1` by `gh api .../compare/1c3233a1...v1.1.1` → `ahead`). Field-by-field list: [docs/api.md @ v1.0.0 §"v1 conversion tips (from v1beta3)"](https://github.com/kubernetes/kubernetes/blob/v1.0.0/docs/api.md) | `v1` is v1beta3 with a rename pass, not a redesign — which is exactly the point. The pre-1.0 plan (["Kube 1.0 should have API v1 without v1beta\* API versions"](https://github.com/kubernetes/kubernetes/blob/v1.1.1/docs/design/versioning.md)) was to ship the final shape *before* 1.0 so users could migrate their stored objects off beta while still on a 0.x release, letting 1.0 drop the beta versions "with no effect". The beta window existed to absorb the renames; `v1` froze them. |
| "the Kubernetes API at `/api/v1beta3`" | `/api/v1` for the core group; every other group lives at `/apis/<group>/<version>` | Group-versioned URL layout landed with API groups in **v1.1** — see A3 | Per the [multiple-API-groups proposal](https://github.com/kubernetes/kubernetes/blob/v1.1.1/docs/proposals/api-group.md): "for `/api/v1`, we set the prefix=`api`, group=`""`, version=`v1`, so the URL remains to be `/api/v1`." The core group kept the legacy path deliberately, "so existing v1 config files will remain valid" — which is why core objects to this day carry a bare `apiVersion: v1` with no group name. |

#### Why the API is versioned at all, and the alpha/beta/GA conventions

| What the post says | What is true at the pin | Changed in | The decision behind it |
|---|---|---|---|
| "the API is in beta, expect changes" / no stability contract stated | A written, enforced policy: alpha = `v1alpha1` (may vanish any release, no notice); beta = `v1beta1` (deprecated ≤ 9 months or 3 minor releases after introduction, then served for a further 9 months or 3 minor releases, whichever is longer); GA = `v1` (not removed within a major version) | At v1.0 there was no policy: [docs/api.md @ v1.0.0](https://github.com/kubernetes/kubernetes/blob/v1.0.0/docs/api.md) says "The precise deprecation policy for eliminating features is TBD, but once we reach our 1.0 milestone, there will be a specific policy." The numbered-rule document was **first published 2017-01-03** ([kubernetes/website PR #1856 "Add deprecation policy"](https://github.com/kubernetes/website/pull/1856), original path `docs/deprecation-policy.md`) — i.e. the v1.5-era docs. Current text: [Deprecation Policy](https://kubernetes.io/docs/reference/using-api/deprecation-policy/) (Rules #1, #3, #4a, #4b) and [api_changes.md §"Alpha, Beta, and Stable Versions"](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api_changes.md) | Rule #1 — "API elements may only be removed by incrementing the version of the API group" — is the whole reason versions exist. Objects are serialised in versioned form into etcd, so a field's meaning can never be changed in place; the only safe way to restructure is to stand up a new group-version, convert through an internal representation, and retire the old one on a published clock. |
| A YAML uses a `v1beta1` group-version and the post says "just enable it" / assumes it is on | New beta APIs are **off by default** and must be turned on with `--runtime-config`. Beta APIs that existed before v1.24 kept their old default | **v1.24** — [KEP-3136 "Beta APIs Are Off by Default"](https://github.com/kubernetes/enhancements/tree/master/keps/sig-architecture/3136-beta-apis-off-by-default), `kep.yaml`: `status: implemented`, `stage: stable`, `milestone.stable: "v1.24"`. Also stated in [api_changes.md](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api_changes.md): "beta APIs introduced before v1.24 were enabled by default, but this changed for new beta APIs" | Beta-on-by-default made beta a de-facto GA: production users adopted `v1beta1` because it was simply *there*, and then the 9-month removal clock became a breaking change for them. Turning it off forces an explicit opt-in, which is what "beta" was always supposed to mean. The companion KEP is [1635 Prevent PermaBeta](https://github.com/kubernetes/enhancements/tree/master/keps/sig-architecture/1635-prevent-permabeta). |
| Post issues a request against a deprecated version and nothing complains | The apiserver returns an RFC7234 `Warning` header, annotates the audit event `"k8s.io/deprecated":"true"`, and increments `apiserver_requested_deprecated_apis` | **v1.19** — [Deprecation Policy §"deprecated API versions"](https://kubernetes.io/docs/reference/using-api/deprecation-policy/) | Silence is why the v1.16 wave hurt. Making deprecated use *observable* — client-visible warning, cluster-visible metric, audit-visible annotation — turns a surprise at upgrade into a dashboard you can act on months earlier. |

##### What a 2015 post's YAML must literally become

- `apiVersion: v1beta1` / `v1beta2` → `apiVersion: v1`, **and restructure**: `id`→`metadata.name`; labels/annotations into `metadata`; `desiredState`→`spec`; `currentState`→`status`; `entrypoint`→`command` and old `command`→`args`; `hostDir`→`hostPath`; `restartPolicy: {always: {}}`→`restartPolicy: Always`; `imagePullPolicy: PullAlways`→`Always`; resources as `resources: {limits: {cpu: ...}}` with suffixes instead of milli-scaled scalars; volume source inlined into the volume. ([docs/api.md @ v1.0.0 §"v1beta3 conversion tips"](https://github.com/kubernetes/kubernetes/blob/v1.0.0/docs/api.md))
- `apiVersion: v1beta3` → `apiVersion: v1`, **and rename**: `service.spec.portalIP`→`clusterIP`; `createExternalLoadBalancer: true`→`spec.type: LoadBalancer`; `publicIPs`→`spec.type: NodePort`; `pod.spec.host`→`pod.spec.nodeName`; `privileged`/`capabilities`→ under `securityContext`. ([same doc, §"v1 conversion tips (from v1beta3)"](https://github.com/kubernetes/kubernetes/blob/v1.0.0/docs/api.md))
- `apiVersion: extensions/v1beta1` + `kind: Deployment|ReplicaSet|DaemonSet` → `apiVersion: apps/v1`, **and add `spec.selector`** (required and immutable), and accept the new defaults: `maxSurge`/`maxUnavailable` `1`→`25%`, `revisionHistoryLimit` unbounded→`10`, `progressDeadlineSeconds` none→`600`, DaemonSet `updateStrategy.type` `OnDelete`→`RollingUpdate`. Delete `spec.rollbackTo` and `spec.templateGeneration` — they do not exist in `apps/v1`. ([deprecation-guide §v1.16](https://kubernetes.io/docs/reference/using-api/deprecation-guide/#v1-16))
- `apiVersion: extensions/v1beta1` + `kind: Ingress` → `apiVersion: networking.k8s.io/v1`, restructure the backend, and add `pathType` to every path.

#### Traps — API surface

- **Old YAML that still parses but is rejected for a different reason.** `apiVersion: extensions/v1beta1` does not fail with "unknown field"; it fails at the *discovery* layer — `no matches for kind "Deployment" in version "extensions/v1beta1"`. Readers conclude their kubectl is broken or their cluster is missing a CRD. The `extensions` group has no registry directory at all at v1.37.0 (`gh api repos/kubernetes/kubernetes/contents/pkg/registry?ref=v1.37.0` lists no `extensions`), so there is no `--runtime-config` flag that brings it back — unlike the v1.14–v1.15 era, when [PR #72249](https://github.com/kubernetes/kubernetes/pull/72249) explicitly allowed per-resource enablement inside `extensions/v1beta1` and the [v1.16 CHANGELOG](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.16.md) documented `--runtime-config=extensions/v1beta1/deployments=true` as a temporary escape hatch. A post from that window tells you the escape hatch exists. It doesn't any more.
- **The Go packages still exist.** `staging/src/k8s.io/api/extensions/v1beta1`, `apps/v1beta1` and `apps/v1beta2` are all still present in the tree at `ref=v1.37.0`. Code that imports `k8s.io/api/apps/v1beta1` compiles fine and only fails at runtime against a real apiserver. A reader who "verifies" an old client-go snippet by building it learns nothing.
- **YAML that validates and means something different.** An `extensions/v1beta1` Deployment with no `spec.selector` was legal — the selector was defaulted from the pod template labels. In `apps/v1` the selector is required *and immutable*. A mechanical `apiVersion` bump therefore either fails validation, or, if the author "fixes" it by pasting in a selector that differs from the template labels, produces a Deployment whose ReplicaSets adopt nothing.
- **Defaults changed silently under the same field names.** A post that says "rolling update replaces one pod at a time" was describing `extensions/v1beta1`'s `maxUnavailable: 1` / `maxSurge: 1`. The identical YAML under `apps/v1` gets `25%`/`25%`. On a 100-replica Deployment that is a 25-pod-wide rollout, not a 1-pod-wide one. Same for `revisionHistoryLimit` (all → 10) and DaemonSet `updateStrategy` (`OnDelete` → `RollingUpdate` — an old DaemonSet post that says "pods are only replaced when you delete them" is now describing an automatic rollout).
- **Announced removal releases slipped.** Ingress `extensions/v1beta1` was announced for v1.18 (in the v1.14 CHANGELOG), then v1.20 (v1.16 CHANGELOG), and actually went in v1.22. A post from 2019 quoting "removed in 1.18" is citing a plan, not the outcome. Only the [migration guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/) records what happened.
- **`/api/v1` vs `/apis/<group>/<version>` is not a typo.** Posts that construct URLs by hand break on the core group, which has an empty group name and the legacy `/api` prefix by deliberate design ([api-group.md](https://github.com/kubernetes/kubernetes/blob/v1.1.1/docs/proposals/api-group.md)).
- **A beta version being "available" is not the same as it being on.** From v1.24 ([KEP-3136](https://github.com/kubernetes/enhancements/tree/master/keps/sig-architecture/3136-beta-apis-off-by-default)), a *newly introduced* beta API is not served unless enabled. A post that says "just apply this `v1beta1` manifest" may be correct about the API existing and wrong about your cluster serving it — and the error looks identical to the removed-API error above.
- **The migration guide is silent about alpha.** Nothing in it covers `v1alpha*`, yet alpha versions do get deleted (`storage.k8s.io/v1alpha1` VolumeAttributesClass in v1.35). A reader who checks the guide and finds nothing concludes their alpha manifest is still fine.

### Workload objects

#### ReplicationController → ReplicaSet → Deployment

| What the post says | What is true at the pin | Changed in | The decision behind it |
|---|---|---|---|
| `kind: ReplicationController` is how you run N copies of a pod | ReplicationController **still exists and is still served** as `apiVersion: v1` — it is *not* deprecated in any machine-readable sense. Verified at v1.37.0: `pkg/registry/core/replicationcontroller` exists ([tree](https://github.com/kubernetes/kubernetes/tree/v1.37.0/pkg/registry/core)); RC's type carries only `+k8s:prerelease-lifecycle-gen:introduced=1.0` with **no** `deprecated=`/`removed=` marker; it appears nowhere in the [migration guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/). Docs: [ReplicationController concept page](https://kubernetes.io/docs/concepts/workloads/controllers/replicationcontroller/) | RC is a *correct* object with a *weak* selector. Removing it would break stored objects and buy nothing (Rule #1 forbids changing `v1` in place anyway), so it was left served and editorially demoted instead. Say "legacy, still works, don't write new ones" — not "deprecated". |
| `spec.selector: {app: nginx}` — a flat map — is how you select pods | `apps/v1` uses a `LabelSelector`: `spec.selector.matchLabels` and/or `spec.selector.matchExpressions` (`In`, `NotIn`, `Exists`, `DoesNotExist`). | A rolling update is something you run: `kubectl rolling-update foo foo-v2 --image=…` | Rollout is a **server-side** property of a Deployment. You observe it with `kubectl rollout status` and reverse it with `kubectl rollout undo` | Deployment introduced **v1.1** (alpha, `extensions/v1beta1`), beta **v1.2**; `kubectl rolling-update` **removed in v1.18** ([PR #88057](https://github.com/kubernetes/kubernetes/pull/88057), [CHANGELOG-1.18](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.18.md): "The deprecated command `kubectl rolling-update` has been removed") | The old rollout lived **in the client**. From [`docs/design/simple-rolling-update.md`](https://github.com/kubernetes/kubernetes/blob/v1.2.0/docs/design/simple-rolling-update.md): "Whenever the rolling update command executes, **the kubectl client looks for** replication controllers called `foo` and `foo-next`"; crash recovery was smuggled into annotations `desired-replicas` and `update-partner`; and the doc concedes "Obviously there is a race here, where if you kill the client between delete foo, and creating the new version of 'foo' you might be surprised about what is there." A rollout that only exists while a laptop process is alive cannot be audited, resumed by anyone else, or driven by a CI job — so it was moved into a controller. The [Deployment proposal](https://github.com/kubernetes/kubernetes/blob/v1.2.0/docs/proposals/deployment.md) states the goal ("**declarative** config updates") and the property that makes it work: "**DeploymentController is stateless so that it can recover in case it crashes during a deployment.**" |
| (a 2015 post) "a Deployment spins up a **ReplicationController**" | A Deployment owns **ReplicaSets**, one per pod-template revision, distinguished by the `pod-template-hash` label | **v1.2** — [PR #19840 "Move Deployments to ReplicaSets and switch the Deployment selector to the new LabelSelector"](https://github.com/kubernetes/kubernetes/pull/19840). The original proposal genuinely said RC: "Users will be able to create a Deployment, which will spin up a ReplicationController to bring up the desired pods" ([proposal @ v1.2.0](https://github.com/kubernetes/kubernetes/blob/v1.2.0/docs/proposals/deployment.md)) | Deployment needs `matchExpressions` to talk about "every revision of this app", so its child had to be the object with the expressive selector. This is the actual controller split: **ReplicaSet owns replica count; Deployment owns revision history and rollout policy.** Two controllers, two levels, one stored template hash joining them. |
| `apiVersion: extensions/v1beta1`, `kind: Deployment` | `apiVersion: apps/v1` | Group-version walk: **v1.1** `extensions/v1beta1` (alpha) → **v1.2** beta → **v1.6** `apps/v1beta1` ([PR #39683](https://github.com/kubernetes/kubernetes/pull/39683), "Introduce apps/v1beta1.Deployments resource with modified defaults") → **v1.8** `apps/v1beta2` ([PR #48746](https://github.com/kubernetes/kubernetes/pull/48746)) → **v1.9 GA `apps/v1`** ([PR #53679](https://github.com/kubernetes/kubernetes/pull/53679), [CHANGELOG-1.9](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.9.md): "The core workloads API, which is composed of the DaemonSet, Deployment, ReplicaSet, and StatefulSet kinds, has been promoted to GA stability in the apps/v1 group version"). Old versions stopped being served in **v1.16** | Each hop existed to change a **default** or a **constraint**, which Rule #1 forbids doing in place. `apps/v1beta1` was created specifically to carry different defaults from `extensions/v1beta1`; `v1beta2` made the selector required and non-defaulted; `v1` froze it. |
| — | **v1.9 also flipped cascading delete at the REST level**: "The default garbage collection policy for Deployment, DaemonSet, StatefulSet, and ReplicaSet has changed from **OrphanDependents to DeleteDependents** when the deletion is requested through an `apps/v1` endpoint" | **v1.9** — [PR #55148](https://github.com/kubernetes/kubernetes/pull/55148) | Orphaning by default meant deleting a Deployment left its ReplicaSets and Pods running — surprising to everyone and a common source of "ghost" pods. |
| `spec.rollbackTo: {revision: 2}` / POST to the `rollback` subresource | Neither exists. `apps/v1` has no `RollbackTo` field and no `DeploymentRollback` kind. `kubectl rollout undo` is now a **client-side PATCH**: it reads the target revision's ReplicaSet, strips `pod-template-hash`, and patches the Deployment's pod template ([`polymorphichelpers/rollback.go`](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/kubectl/pkg/polymorphichelpers/rollback.go)) | Deprecated in **v1.8** ([PR #49340](https://github.com/kubernetes/kubernetes/pull/49340)); never carried into `apps/v1`, so effectively removed in **v1.9** and unserveable from **v1.16**. Listed under v1.16 notable changes: "`spec.rollbackTo` is removed" ([deprecation-guide §deployment-v116](https://kubernetes.io/docs/reference/using-api/deprecation-guide/#deployment-v116)) | A write-only "do a thing" field inside a `spec` is not declarative — `kubectl apply` of the same manifest would re-trigger the rollback forever, and the field's value was meaningless after the fact. Rollback was re-expressed as "set the spec back to what it was", which `apply` and GitOps can both represent. |

|---|---|---|---|

[KEP-753 `kep.yaml`](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/753-sidecar-containers/kep.yaml): `status: implemented`, `stage: stable`, `milestone: {alpha: v1.28, beta: v1.29, stable: v1.33}` | A plain second container has no defined ordering relative to the app container and no defined shutdown ordering. That broke two things concretely: a service-mesh proxy that starts *after* the app misses the app's first outbound calls, and a log-shipping sidecar that never exits keeps a Job's pod `Running` forever. Encoding "runs for the whole pod lifetime, starts first, terminates last, doesn't count for completion" as a real API field is what makes both cases correct without an in-pod supervisor. **Status at the pin: GA, unconditional, no gate to enable.** |

#### Traps — workload objects

- **"ReplicationController is deprecated" is wrong at the pin, and the correction matters.** RC is served, unmarked in the prerelease-lifecycle generator, absent from the migration guide, and was still receiving code changes in v1.37. An exercise that tells a learner "this API is deprecated, migrate off it" is teaching a false fact; the true statement is "legacy, superseded, still fully supported, no removal scheduled". Meanwhile the thing that *is* gone — `extensions/v1beta1` Deployment — is the object the 2015 post probably reached for as the *modern* alternative.
- **The 2015 Deployment posts describe a Deployment managing ReplicationControllers.** That was genuinely true in the [original proposal](https://github.com/kubernetes/kubernetes/blob/v1.2.0/docs/proposals/deployment.md) and stopped being true inside the same release cycle ([PR #19840](https://github.com/kubernetes/kubernetes/pull/19840)). A reader who follows the post will look for RCs under `kubectl get rc` after creating a Deployment, find nothing, and conclude the Deployment failed.
- **`kubectl rolling-update` still appears to exist in muscle memory but is gone since v1.18** — and its replacement is not a command that *does* the rollout, it is a command that *watches* one (`kubectl rollout status`). The conceptual move — from "run the rollout" to "declare the target and observe convergence" — is the actual lesson, and a post that predates it teaches the opposite mental model.
- **Defaults changed under identical field names, with no conversion.** `maxSurge`/`maxUnavailable` `1`→`25%`, `revisionHistoryLimit` unbounded→`10`, `progressDeadlineSeconds` never→`600`, DaemonSet `updateStrategy` `OnDelete`→`RollingUpdate`. A post that says "one pod at a time" or "DaemonSet pods are only replaced when deleted" is factually describing `extensions/v1beta1` behaviour while the reader's YAML now says `apps/v1`. Nothing errors; the rollout is just wider and faster than described. (Driving issues: [#23597](https://github.com/kubernetes/kubernetes/issues/23597) unbounded ReplicaSet accumulation, [#23304](https://github.com/kubernetes/kubernetes/issues/23304) single-replica downtime.)
- **`spec.selector` flipped from "helpfully defaulted" to "required and immutable".** `extensions/v1beta1` defaulted it from the pod template labels; `apps/v1` does not, and `ValidateDeploymentUpdate` / ReplicaSet / DaemonSet / StatefulSet validation all call `ValidateImmutableField` on it. Reason from [CHANGELOG-1.8](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.8.md): "a `spec.selector` default value is no longer available, because **it's incompatible with `kubectl apply` and strategic merge patch**." A learner who "fixes" the validation error by inventing a selector that doesn't match the template gets a Deployment stuck at 0 available replicas with no error message.
- **PetSet→StatefulSet is not a rename you can apply to a live object.** The v1.5 notes require migration steps before *and* after upgrading; there was no in-place conversion because `apps/v1alpha1` was deleted. A post that says "PetSet is now called StatefulSet, just update the kind" understates it.
- **Job's migration is to delete YAML, not add it.** Every other workload object gained a required `spec.selector`; Job lost the recommendation to write one. Copying a `spec.selector` out of a 2015 Job post into a `batch/v1` Job produces two Jobs that fight over each other's pods.
- **The sidecar feature gate is gone, which cuts both ways.** From v1.34 the `LegacySidecarContainers` escape hatch no longer exists ([PR #131463](https://github.com/kubernetes/kubernetes/pull/131463)) and from v1.37 the `SidecarContainers` gate itself is gone ([PR #137755](https://github.com/kubernetes/kubernetes/pull/137755)). A 2023–2024 post that says "enable the `SidecarContainers` feature gate" describes a flag that will now cause the component to **fail to start on an unknown flag**, not a no-op. Also note v1.33's own changelog predicted the gate's removal in v1.36; it actually happened in v1.37 — cite the removal, not the prediction.
- **`kubernetes.io/created-by` is gone (v1.9, [PR #54445](https://github.com/kubernetes/kubernetes/pull/54445)).** Posts that teach "find the controller that made this pod" via that annotation now find nothing; use `metadata.ownerReferences` with `controller: true`.

#### `kubectl run`, the generator era, and imperative → declarative

| What the post says | What is true at the pin | Changed in | The decision behind it |
|---|---|---|---|
| `kubectl run-container nginx --image=nginx` | `kubectl run nginx --image=nginx` | Renamed in **v0.18.0** ([PR #8596](https://github.com/kubernetes/kubernetes/pull/8596), "Kubectl command renaming (run-container to run and resize to scale)", in the [v0.18.0 release notes](https://github.com/kubernetes/kubernetes/releases/tag/v0.18.0)); the hidden `run-container` alias was **removed in v1.13** ([PR #70728](https://github.com/kubernetes/kubernetes/pull/70728): "The deprecated command `run-container` has been removed. #### Traps — kubectl

- **`kubectl run` is the single most dangerous command in an old post, because it still exists and still succeeds.** A 2016 tutorial's `kubectl run nginx --image=nginx` printed `deployment "nginx" created`; at the pin the identical command prints `pod/nginx created`. Nothing warns you. The follow-up steps in the post — `kubectl get deployments`, `kubectl scale deployment nginx`, `kubectl rollout status`, `kubectl delete deployment nginx` — then all fail on a missing object, and a learner reasonably concludes their cluster is broken. If a post's narrative depends on `run` producing a controller, the exercise must replace the command, not just the flags.
- **`--replicas=3` on `run` failed loudly for three releases and now fails differently.** v1.18–v1.20 accepted it and silently ignored it (`MarkDeprecated("replicas", "has no effect…")`) — so a copy-pasted command on a v1.19 cluster created *one* pod and reported success. From v1.21 it is an unknown-flag error. The "accepted but inert" window is the nastiest state to reproduce in a lab and worth calling out explicitly.
- **`kubectl apply` is still client-side by default at the pin.** Posts from 2021 onward often assert that "apply is now server-side"; it is not, unless you pass `--server-side`. Verified two ways at v1.37.0 (the flag defaults to `false`; `--field-manager` defaults to `kubectl-client-side-apply`). So the `last-applied-configuration` annotation a 2016 post describes is *still being written to your objects* — the old post is more accurate here than the newer one.
- **CHANGELOG entries lie about their own removals, in both directions.** Three confirmed cases: CHANGELOG-1.8 announced removal of the `run-container` alias, which a bad conflict resolution in [PR #50998](https://github.com/kubernetes/kubernetes/pull/50998) reinstated two days later — it actually died in **v1.13**; `--export` was announced for v1.18 and removed in **v1.19**; `kubectl convert` was announced for v1.17 and removed in **v1.20**. Never date a kubectl removal from the announcement — check the source tree at the release tag. (Corollary: CHANGELOG-1.20's "Generators for services are removed from kubectl" overclaims; `kubectl expose --generator` survived to **v1.24**.)
- **A deprecated flag disappears from the docs before it disappears from the binary.** `MarkDeprecated` hides a flag from `--help` and therefore from the generated reference pages. `--record` is the live example: absent from [the docs](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_apply/), present and functional at v1.37.0. Absence from the reference page is not evidence of removal.
- **`kubectl get pods` output shape has drifted independently of any flag.** `--show-all` is gone because terminated pods are now always shown; `kubectl describe service`/`ingress` read **EndpointSlices instead of Endpoints** from **v1.31** ([PR #124598](https://github.com/kubernetes/kubernetes/pull/124598)); `kubectl get`/`describe` stopped reporting counts for referenced tokens and secrets in **v1.35** ([PR #117160](https://github.com/kubernetes/kubernetes/pull/117160)); `kubectl describe` shows events only for single-object describes from **v1.36** unless you pass `--show-events` ([PR #137145](https://github.com/kubernetes/kubernetes/pull/137145)). Any exercise that greps or diffs kubectl's human-readable output against a transcript from an old post will mismatch on whitespace and on content.
- **Flag renames that a post will hit outside `run`:** `kubectl drain --delete-local-data` → `--delete-emptydir-data` (old form dropped **v1.31**, [PR #125842](https://github.com/kubernetes/kubernetes/pull/125842)); `kubectl apply --prune-whitelist` → `--prune-allowlist` (**v1.30**, [PR #120246](https://github.com/kubernetes/kubernetes/pull/120246)); `kubectl autoscale --cpu-percent` began deprecation in favour of `--cpu`/`--memory` (**v1.34**, [PR #129373](https://github.com/kubernetes/kubernetes/pull/129373)).
- **The commands a 2015 post uses that no longer exist at all:** `run-container`, `resize`, `rollingupdate`, `rolling-update`, `log`, `clusterinfo`, `apiversions`, `update`, `stop`, `convert`, `minions`. Every one of these produces "unknown command", which is at least a loud failure — unlike `run`, `apply`, and `--record`, which fail quietly.
- **[UNVERIFIED] `kubectl expose --generator` may never have had a formal deprecation release.** No `MarkDeprecated("generator", …)` appears in `expose.go` at any tag v1.19.0–v1.23.0 (only `--container-port` carried one), and the v1.18 blanket deprecation ([PR #88655](https://github.com/kubernetes/kubernetes/pull/88655)) patched the `cmdutil.AddGeneratorFlags` helper that `expose.go` does not use. Tried: CHANGELOG-1.16→1.24 greps for `expose`+`generator`, PR search, and the full commit history of `expose.go`. Removal in **v1.24** ([PR #106824](https://github.com/kubernetes/kubernetes/pull/106824)) is solid; the deprecation date is not — do not put one in an exercise.
- **[UNVERIFIED] the "kubectl died mid-rollout so the rollout stalled" framing.** The *mechanism* is fully documented ([`simple-rolling-update.md`](https://github.com/kubernetes/design-proposals-archive/blob/main/cli/simple-rolling-update.md): client-driven loop, `desired-replicas`/`update-partner` crash-recovery annotations, "Recovery is achieved by issuing the same command again"), but no primary source states that sentence. Teach the mechanism, not the slogan.

#### Traps — security, authorization, policy

- **`--authorization-mode` still defaults to `AlwaysAllow`.** This is the most dangerous "nothing changed" in the whole area. A reader who follows a 2015 post to stand up an apiserver by hand — or a lab exercise that starts one directly — gets a cluster with no authorization at all, at v1.37, with no error. Only kubeadm/managed distros save you. Any exercise that spawns a raw apiserver must pass `--authorization-mode=Node,RBAC` explicitly.
- **A PSP manifest is now a hard error, but an *RBAC* manifest referencing PSPs applies cleanly and grants nothing.** `kubectl apply` of a `PodSecurityPolicy` fails outright (good — visible). But the accompanying ClusterRole with `apiGroups: ["policy"], resources: ["podsecuritypolicies"], verbs: ["use"]` applies successfully at v1.37 and is inert. RBAC does not validate that the resource exists. The reader ends up believing pod security is enforced when nothing is enforcing it.
- **`extensions/v1beta1` vs `policy/v1beta1` PSP.** Posts between v1.3 and v1.10 use `extensions/v1beta1`; posts between v1.10 and v1.21 use `policy/v1beta1`. Both are equally dead — but a reader who sees "the apiVersion is wrong" may try to "fix" it forward rather than concluding the whole object is gone.
- **Namespace labels are the silent failure mode of PSA.** A namespace with no `pod-security.kubernetes.io/enforce` label enforces `privileged` — i.e. nothing. Applying a "restricted" workload proves nothing about the namespace's policy. Conversely, an exercise that labels the namespace `enforce: restricted` will break most 2015-era pod manifests (no `runAsNonRoot`, no `seccompProfile`, no `allowPrivilegeEscalation: false`, no dropped capabilities) — that breakage is the lesson, but it needs to be expected.
- **`kubectl get secret` for a ServiceAccount token returns nothing.** Every 2015–2023 post that says "find the token in the `<sa>-token-xxxxx` Secret" is broken since v1.24, and it fails by *absence*, not by error: `kubectl get secrets -n default` just lists nothing. The replacement is `kubectl create token <sa>`. Note the second-order trap: the token you get is short-lived, so a copied-out token in an exercise script will pass once and fail an hour later.
- **Legacy tokens still authenticate.** Auto-*creation* stopped in v1.24; tokens that already exist, or that you deliberately create as a Secret, still work. So "it worked when I tried it on an old cluster" is not evidence the mechanism is current.
- **A v1beta1 NetworkPolicy that was inert becomes enforcing.** Explicitly called out in the v1.7 upgrade notes: policies that had no effect under the namespace-annotation model start isolating pods under v1 semantics. A 2016 post's example policy can block traffic the post says it permits.
- **`rbac.authorization.k8s.io/v1alpha1` fails as "no matches for kind", not as "deprecated".** Disabled by default since v1.8; the error looks like a typo rather than a version problem.
- **Webhook-based policy examples still work, which hides that they are no longer the recommended shape.** A 2019 post's ValidatingWebhookConfiguration applies and functions at v1.37. Nothing tells the reader that a ValidatingAdmissionPolicy would do it without a deployment, a Service, a CA bundle, and a failure-mode decision.

#### Traps — container runtime

- **`docker ps` returns success and an empty (or unrelated) list.** No error, no warning, no hint that the containers exist under containerd. This is the highest-value trap in area B: any 2015–2021 troubleshooting walkthrough that starts with "SSH in and list the containers" leads the reader to conclude their pods never started. The equivalent is `crictl ps` — and it needs the runtime endpoint set, or it "attempts to connect to a list of known endpoints, which might result in an impact to performance."
- **A `--container-runtime=rkt` (or `=docker`) flag makes the kubelet fail to start with an unknown-flag error, not a deprecation warning.** Removed in v1.27. An exercise that copies a 2015 kubelet unit file gets a dead kubelet with a message that does not mention CRI.
- **The kubelet refusing to start on a cgroup v1 node looks like a broken install.** From v1.35 this is the *intended* behaviour, and the fix (`failCgroupV1: false`) is a kubelet config field, not a flag — so it is invisible to anyone grepping `--help`. Any lab built on an old base image (or an old CI runner) can hit this.
- **The cgroup driver mismatch produces no error at all.** kubelet on `cgroupfs` and runtime on `systemd` starts fine and runs pods; the symptom is wrong/unstable resource accounting under load. Since v1.34 `KubeletCgroupDriverFromCRI` may silently *ignore* the `cgroupDriver` you set — so a post telling you to set it, and an exercise verifying that it took effect, can both be "right" and disagree.
- **"Removal is planned for v1.22" is in every 2021-vintage post.** The reader who checks "am I affected?" against v1.22 concludes wrongly. The real boundary is v1.24.
- **Docker being *installed* on a node proves nothing.** Many node images still ship the Docker CLI/daemon; its presence makes the old commands run, which is worse than them being absent. The question is never "is Docker there", it is "what socket does the kubelet's `containerRuntimeEndpoint` point at".
- **`cri-dockerd` means "you can still use Docker Engine" — but it is a third-party component outside the Kubernetes project.** A post saying "Docker still works" and a post saying "Docker was removed" are both accurate about different things; the distinction is in-tree adapter (gone) vs out-of-tree adapter (exists, separately maintained).
- **Old `securityContext` examples get quietly stronger guarantees than they claim, and older ones get weaker ones.** A pre-v1.31 post describing AppArmor via annotation would have run *unconfined* on a node without AppArmor; at the pin the pod is rejected. So a 2018 exercise "proving" a profile was applied may never have proven anything.
- **`hostUsers`/user namespaces change what `runAsUser: 0` means.** Posts explaining "never run as root in a container" are still good advice but their stated *reason* (container uid 0 == host uid 0) is no longer unconditionally true at v1.37.

#### Traps — networking

- **`--proxy-mode=userspace` is not a mode you can fall back to.** Readers treat it as the safe, boring option; it has been out of the tree since v1.26. Relatedly, the userspace proxy used to open a real listening socket per Service on the node, so any 2015 troubleshooting advice of the form "run `netstat` on the node and look for kube-proxy's port for your Service" finds nothing on any supported cluster — iptables/ipvs/nftables modes do DNAT with no listener at all. The one exception is new and narrow: v1.37's opt-in userspace TCP proxy for localhost NodePorts in nftables mode.
- **"iptables is the default" is correct today and wrong from 1.40, and the warning is easy to miss.** v1.37 kube-proxy logs a warning when the mode was *defaulted* rather than set. Any cluster that has never written an explicit `mode:` is scheduled to silently change its entire service data path on a future upgrade. The actionable advice is to write the mode down now, whichever one you want.
- **`spec.topologyKeys` is silently ignored, not rejected.** It was removed from the schema in v1.22 rather than made invalid, so a manifest carrying it applies cleanly and routes traffic with no topology awareness whatsoever, with no warning. The same shape of trap applies to `service.kubernetes.io/topology-aware-hints`: renamed in v1.27 (both forms accepted, and they must agree), and its successor `service.kubernetes.io/topology-mode` was itself deprecated in v1.33 and will never go GA.
- **`kubernetes.io/ingress.class` is an annotation, so it cannot fail validation.** A `networking.k8s.io/v1` Ingress carrying the old annotation and no `ingressClassName` is accepted unconditionally. Whether it works depends entirely on whether that particular controller still honours the legacy annotation — several do, several don't, and none of them tell the API server. The symptom is "my Ingress exists and never gets an address".
- **`pathType` reverses the direction of the default.** In `v1beta1` the field was absent or `ImplementationSpecific`; in `v1` it is required with **no default**. So a converted manifest either fails to apply (loud, fine) or — if a conversion tool fills it in — gets `Prefix` semantics where regex-ish behaviour was assumed. As `Prefix`, `/foo/bar` matches `/foo/bar/baz` but **not** `/foo/barbaz`; a regex interpretation may have matched both. Routing changes quietly.
- **`kubectl get endpoints` still works, and that is the problem.** The Endpoints controller still runs at v1.37, so the command returns plausible output forever — but kube-proxy has not read Endpoints in years, Gateway API conformance forbids implementations from using them, and dual-stack, topology hints and Services above ~1000 endpoints are simply not represented there. Debugging a routing problem through `kubectl get endpoints` is debugging a mirror, not the data path.
- **`kubenet` is gone but still reads like an option.** Old posts (and some docs pages) mention it without stating the removal, which is only visible as a side effect of dockershim's deletion in v1.24. There is no "use kubenet if you don't need a real CNI plugin" fallback, and `--network-plugin=cni` is not a deprecated kubelet flag — it is an *unknown* flag, so the kubelet refuses to start.
- **Gateway API version numbers are not Kubernetes version numbers, and per-resource maturity is a third axis.** At v1.6.1, HTTPRoute/GRPCRoute/TLSRoute/TCPRoute/UDPRoute are all `v1` Standard — but installing the **Experimental** channel gets you resources (`XBackend`, SessionPersistence) whose names and API group will change on graduation; the v1.3.0 notes state that migrating to Standard "will require recreating these resources with the standard channel names and API Group (both lacking the `x` prefix)". An `x`-prefixed resource in production is a scheduled rewrite.
- **"Ingress is deprecated" is wrong in a way that matters.** Ingress is *frozen*: full GA stability guarantees, no removal planned, and Gateway API's own FAQ says "There are no plans to deprecate this API." Do not schedule an Ingress migration against an imaginary removal deadline — but do migrate if you need any feature invented after 2020, because none will ever land in Ingress.
- **`ndots:5` did not change, so every stale DNS-tuning post is still live advice — including the bad parts.** What *did* change is the tooling: `dnsConfig.searches` accepts 32 entries / 2048 chars since v1.28, and since v1.34 `searches: ["."]` suppresses cluster-domain expansion entirely. A post that says "you can't fix search-path amplification, just use FQDNs everywhere" is describing a constraint that no longer holds.

#### Traps — storage

- **The API still accepts every dead volume type.** At `release-1.37`, `core/v1` `VolumeSource` and `PersistentVolumeSource` still declare `awsElasticBlockStore`, `gcePersistentDisk`, `azureDisk`, `azureFile`, `cinder`, `vsphereVolume`, `rbd`, `cephfs`, `glusterfs`, `portworxVolume`, `quobyte`, `storageos`, `scaleIO`, `flocker` and `gitRepo`. Deprecation policy forbids removing GA API fields, so a 2015 manifest is **validated and accepted**: `kubectl apply` succeeds, the PV is created, the Pod is admitted and scheduled — and then the kubelet has no plugin for it. The failure is a mount-time event on a node minutes later, not an admission error in CI.
- **There are two very different kinds of "removed", and readers will conflate them.** For `awsElasticBlockStore`, `gcePersistentDisk`, `azureDisk`, `azureFile`, `cinder`, `vsphereVolume` and `portworxVolume`, `csi-translation-lib/plugins/` still ships a translator at v1.37, so the old spec is rewritten into a CSI spec at bind/mount time — those manifests work **if and only if** the matching CSI driver is installed. Same YAML, same cluster version, works or doesn't depending on a Deployment that appears nowhere in the manifest. For `rbd`, `cephfs`, `glusterfs`, `quobyte`, `storageos`, `scaleIO` and `flocker` there is **no** translator: unconditionally dead, and per the v1.31 notes "a re-deployment of your application is required". Anyone who learns the slogan "in-tree plugins were migrated to CSI" will assume the first case covers Ceph. It does not.
- **The `azureFile` CHANGELOG is wrong.** CHANGELOG-1.28 says "Removed the deprecated `azureFile` in-tree storage plugin" (PR #118236); that commit was reverted on 2023-06-02, and `pkg/volume/azure_file` is present on both `release-1.28` and `release-1.29`. The real removal was PR #122576 in **v1.30**. Citing CHANGELOGs without checking the tree publishes a wrong release number here.
- **Annotations that are ignored rather than rejected.** `volume.alpha.kubernetes.io/storage-class` has had no meaning since v1.6, so a 2015 manifest relying on it produces a PVC with *no* class, which then either binds to nothing or silently picks up the cluster default — neither is an error. Meanwhile `volume.beta.kubernetes.io/storage-class` *does* still work at v1.37, but only as a fallback: add `spec.storageClassName` later and the annotation is silently outranked, provisioning from a different class. And **both** `is-default-class` annotation names (`storageclass.` and `storageclass.beta.`) are still read, so a cluster can have a default set through a path nobody thinks to check.
- **A PVC that stays `Pending` forever, and is working correctly.** With `volumeBindingMode: WaitForFirstConsumer` — the default in most modern StorageClasses, including cloud CSI and in-tree `local` — `kubectl get pvc` shows `Pending` and `describe` says `waiting for first consumer to be created before binding`. A reader whose 2015 mental model is "create the PVC, watch it Bind, then create the Pod" concludes storage is broken and starts debugging the driver. Nothing is broken. **The inverse is worse:** a StorageClass copied from an old post *without* `volumeBindingMode` gets `Immediate`, silently reintroducing exactly the zonal-stranding bug the field was created to fix — invisible until a Pod becomes unschedulable in a zone that has the disk but no CPU.
- **`gitRepo` fails at mount time, in a security-relevant way, and its error message lies to you.** The field validates, the Pod is admitted, the plugin is still listed in `cmd/kubelet/app/plugins.go` — and `SetUp` tells you to enable `GitRepoVolumeDriver`, a gate that has been `LockToDefault: true` since v1.36 and therefore cannot be enabled. The reason it is locked shut is CVE-2024-10220, root RCE on the node via git hooks — name that in any exercise, or someone "fixes" it with a fork or an initContainer that shells out to `git` as root.
- **`emptyDir: {medium: Memory}` with a `sizeLimit` used to be a lie.** On any cluster before v1.32 the tmpfs was sized at 50% of *host* memory regardless of `sizeLimit`. A post from that era that pairs `medium: Memory` with a small `sizeLimit` and calls it a memory cap is describing a bound that was not enforced; at the pin it is. Note also that tmpfs bytes count against the writing container's memory limit, so a pod that "worked" under the old unenforced sizing can now hit a different wall.

#### Traps — cluster lifecycle

- **The `KUBERNETES_PROVIDER` variable is silently inert for anything but GCE.** `cluster/kube-up.sh` still exists, so a 2015 post's command still *runs*; it just cannot find the provider directory. Readers conclude their environment is broken rather than that the instruction is a decade stale.
- **A `kubeadm.k8s.io/v1alpha1`/`v1alpha3`/`v1beta1`/`v1beta2`/`v1beta3` config file is a hard parse failure, not a deprecation warning.** kubeadm drops old config API versions outright (v1beta1-and-older gone in v1.22, v1beta2-and-older in v1.27, v1beta3 in v1.37) and `kubeadm config migrate` cannot bridge more than one hop — a v1beta1 file needs kubeadm 1.15–1.21 to get to v1beta2 *first*. Any tutorial with `MasterConfiguration` in it is unusable as written.
- **`kubelet --config` uses strict deserialization since v1.17.** A single misspelled or since-renamed field in a copied `KubeletConfiguration` makes the kubelet refuse to start, with an error about the file rather than about the field's meaning. This is the *opposite* failure mode from flags, which silently ignored typos in some tooling.
- **`kubelet.config.k8s.io/v1beta1` looks like it must be old. It is current.** A reader who "modernises" the apiVersion to `v1` produces a file the kubelet rejects, because `k8s.io/kubelet/config/v1` is the credential-provider API, not `KubeletConfiguration`. The same trap applies in reverse to kube-proxy, whose config API is genuinely still `v1alpha1` at the pin.
- **`--insecure-port=8080` no longer opens a port, and no longer errors either** (the flag is accepted only as `0`, and was removed in v1.24). Every 2015 example that does `curl http://localhost:8080/api/v1/pods` on a control-plane node just hangs or gets connection-refused; the reader has no signal that the *concept* was removed.
- **etcd2→etcd3 is one-way.** A post that says "back up etcd and upgrade" is understating: `etcdctl migrate`/`etcdutl migrate` produces a v3 datadir that cannot be read by the older server, so the only rollback is the pre-migration snapshot. And at the pin the v2 store is not even present in etcd (3.6.0 removed `--enable-v2`), so there is no "just re-enable v2" fallback.
- **A post that says "Salt is in `cluster/saltbase`, edit the pillar to change a kubelet flag"** sends the reader to a directory that 404s. The equivalent operation today is editing the `kubelet-config` ConfigMap in `kube-system` (or `/var/lib/kubelet/config.yaml`) and restarting the kubelet — a completely different mechanism, not a renamed file.
- **Self-hosting sounds like the modern design and is the abandoned one.** "Run the control plane as DaemonSets/Deployments so Kubernetes manages itself" reads as more advanced than static pods, so readers pursue it; it was removed in v1.21 precisely because it is a bootstrap cycle.
- **Version skew asymmetry bites in one direction only.** `kubectl` may be one minor *newer* than the apiserver, but `kubelet` may never be newer. A post that says "just use the latest of everything" is fine for kubectl and a policy violation for nodes.

Latest kube-state-metrics at the pin: **v2.20.0** (2026-08-18, component version). | The two-pipeline model dates from the Heapster deprecation in **v1.11**; the retirement README names it explicitly ("For basic CPU/memory HPA metrics: metrics-server … For general monitoring: a third-party monitoring pipeline that can gather Prometheus-formatted metrics") | The autoscaler needs a *small* number of *current* values with low latency and hard availability requirements; a dashboard needs a *large* number of *historical* values and can tolerate gaps. One component optimised for both is optimised for neither — which is why metrics-server deliberately dropped Heapster's historical store and its sinks. |
| "Node/container metrics live on the kubelet's `/metrics`." | The kubelet splits its Prometheus surface across several endpoints: `/metrics` (kubelet's own), **`/metrics/cadvisor`** (container metrics, added in **v1.8**, commit `f5f989382` "Restore cAdvisor prometheus metrics to the main port"), **`/metrics/probes`** (liveness/readiness probe results, added in **v1.11**), and **`/metrics/resource`** (the resource-metrics endpoint metrics-server scrapes). | `/metrics/cadvisor` **v1.8**; `/metrics/probes` **v1.11**; `/metrics/resource/v1alpha1` deprecated in **v1.18** in favour of `/metrics/resource`, and `metrics/resource/v1alpha1` **removed in v1.20**. `/metrics` and `/metrics/probes` were labelled **ALPHA** stability in **v1.16**. | Container metrics are enormous compared to the kubelet's own, so serving them from one path forced every scraper to pay for both; splitting the paths lets a Prometheus scrape config take cadvisor at a slow interval and probe results at a fast one. `/metrics/resource` exists separately because it is a *minimal, stable* CPU/memory surface designed for metrics-server rather than a general-purpose dump. |
| "Give the metrics collector RBAC on `nodes/stats`." | metrics-server needs **`nodes/metrics`**, not `nodes/stats`, because it scrapes `/metrics/resource` rather than `/stats/summary`. | **metrics-server v0.6.0** (2022-01-20, component version) — "Metrics Server now requires access to `nodes/metrics` RBAC resource instead of `nodes/stats`" + "Migrate to Kubelet resource metrics endpoint" | Reading `/stats/summary` meant metrics-server parsed the whole Summary API — filesystem stats, network stats, per-volume stats — to extract two numbers; scraping the purpose-built `/metrics/resource` cut both the payload and the kubelet's CPU cost of computing stats it did not need. |
| "InfluxDB + Grafana is the standard cluster monitoring stack." | Neither ships with Kubernetes. InfluxDB cluster monitoring was deprecated as part of the Heapster deprecation; Grafana is a fine dashboard but is deployed by the user, typically against Prometheus. | InfluxDB cluster monitoring deprecated **v1.11**; the addon directory removed **v1.18** | The addon locked every cluster into one time-series database chosen in 2014, shipped and CVE-patched by the Kubernetes release team; making the storage layer the user's choice removed a whole class of "Kubernetes ships a database" maintenance from the release process. |
| "The Kubernetes Dashboard shows graphs (it gets them from Heapster)." | The graphs that depended on Heapster's short-term in-memory store were explicitly named as functionality metrics-server does **not** replace ("it doesn't include some features of Heapster, such as short term metrics for graphs in kube-dashboard and dedicated push sinks, which proved hard to maintain and scale"). Dashboards at the pin come from Prometheus/Grafana. | **v1.11** | Serving graph history required Heapster to be a time-series database inside the cluster's critical path; the project judged that job belonged to an actual TSDB, accepting a visible feature regression in the dashboard as the cost. |

#### Traps — monitoring and observability

- **Port 4194 fails closed, silently.** A 2015 post's `curl http://<node>:4194/api/v1.3/subcontainers` gets connection-refused, which reads as a firewall problem. There is nothing to unblock: the server was deleted in v1.12. The reader will spend the debugging time on iptables, not on the docs.
- **`kubectl top` failing is not a cluster fault.** On a cluster with no metrics-server, `kubectl top nodes` errors out. A post from 2015 assumes the monitoring addon was installed by the bootstrap script; at the pin nothing installs it for you unless your distro does. The fix is "install metrics-server", not "fix the API server".
- **`nodes/stats` RBAC still exists as a subresource, so a copied ClusterRole grants a permission that is no longer the one needed.** The apply succeeds; metrics-server then fails to scrape with a 403 on `nodes/metrics`. Nothing in the RBAC output hints at the mismatch.
- **`metrics.k8s.io/v1beta1` manifests and clients still work at the pin, so nothing forces you to notice v1 exists.** Conversely, a reader who sees "GA in v1.37" and writes `metrics.k8s.io/v1` against a 1.36 cluster gets a not-found on the API group — the GA is one release old at the pin, so version-check before recommending it.
- **`autoscaling/v2beta1` and `v2beta2` manifests are rejected, not warned about** (removed in v1.25 and v1.26 respectively). Every HPA example between 2017 and 2021 uses one of them. The error is a plain "no matches for kind" and does not say "use `autoscaling/v2`".
- **The `--horizontal-pod-autoscaler-use-rest-clients` flag is gone from kube-controller-manager (v1.22), so a post that tells you to set it to `false` to "keep using Heapster" makes the controller-manager refuse to start.** This is one of the rare loud failures in this table — worth using as an exercise precisely because it *does* fail loudly.
- **"Heapster is deprecated" understates it by five years.** Some 2018-era posts say "deprecated, still works". At the pin there is no image being rebuilt, no CVE patching, and the HPA cannot consume it at all. Treat any Heapster instruction as delete-and-replace, never as migrate-later.
- **`/metrics/resource/v1alpha1` is a path, not an API version you can negotiate.** A scrape config from 2019 pointing at it returns 404 since v1.20, and Prometheus reports the target as down with an HTTP error — easy to misread as a kubelet auth problem.
