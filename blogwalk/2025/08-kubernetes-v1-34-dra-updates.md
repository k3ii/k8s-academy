# The page this post links six times has moved, so the alias rescues every path and none of the five fragments, the label its one operational sentence turns on is spelled one way in the blog and another in the reference that registers it, and a GA post names no gate and no KEP

**Post** — [Kubernetes v1.34: DRA has graduated to GA](https://kubernetes.io/blog/2025/09/01/kubernetes-v1-34-dra-updates/),
2025-09-01.

7,535 bytes, 109 lines, 996 words of body. The byline is `The DRA team`: of 2025's twelve `walk`
posts it is the only one naming no person at all, with no GitHub handle and no employer beside it.
Six `##` headings and no `###`, no fenced block, no Hugo shortcode, and one line carrying trailing
whitespace. Eighteen markdown links across eighteen distinct targets, of which eight are GitHub
profiles in the acknowledgements and six are one documentation page carrying five different
fragments. Eighth of the year's twelve by publication date, and eighth of the twelve by size.

**As written**

The headline is one sentence long and the post repeats it three ways: the core of DRA has graduated
to General Availability. `:19` calls it the headline feature of the release, `:26-28` says DRA is
now stable, will be part of Kubernetes for the long run, and will get new features without breaking
changes, so driver authors "can start adopting DRA with confidence". `:30-32` draws the operational
consequence: from 1.34, DRA is enabled by default, and so are the DRA features that have reached
beta, because the default API version for DRA is now the stable `v1` rather than the `v1beta1` and
`v1beta2` that needed an explicit opt-in.

Then two lists. *Features promoted to beta* (`:34-55`) gives three: admin access, which now
restricts the `adminAccess` field to users who can create ResourceClaims and ResourceClaimTemplates
in a namespace carrying a particular label (`:39-45`); prioritized list, where a request names
acceptable alternatives in order and the scheduler satisfies the best one available (`:47-51`); and
a kubelet API that reports DRA-allocated resources to node monitoring agents (`:53-55`). *New alpha
features* (`:57-85`) gives four: extended resource mapping, which advertises DRA devices under the
familiar extended-resource request syntax (`:61-65`); consumable capacity, which lets unrelated
claims each take a share of one physical device (`:67-71`); binding conditions, which delay binding
a Pod to a node until an external device is confirmed ready (`:75-79`); and resource health status,
which surfaces device health in Pod status (`:81-83`).

The close is short. *What's next?* (`:87-91`) says the work does not stop, that several alpha and
beta features are planned for GA in the next couple of releases, and to expect "an equally ambitious
set of features in DRA for the 1.35 release". *Getting involved* points at the WG Device Management
Slack channel and meeting document, and *Acknowledgments* thanks eight new contributors by name and
handle. There is no *Learn more* section, no KEP link, no feature-gate name, and no YAML: the only
Kubernetes object kinds written anywhere in the post are ResourceClaim and ResourceClaimTemplate,
once each, in the admin-access paragraph.

**The diff, and why** — four cases, and the one that decides the exercise is that every claim about
the feature held while every address in the prose stopped working.

**Still right.** The GA promise is the part that survived intact. `resource.k8s.io` is still `v1`
three releases later, still serving the same four kinds — DeviceClass, ResourceClaim,
ResourceClaimTemplate and ResourceSlice — with everything since added beside them, `DeviceTaintRule`
at `v1beta2` and `ResourcePoolStatusRequest` at `v1alpha3`. Of the twenty-one gate files that carry
DRA, exactly one has `removed: true`, and its last rung is 1.31, three releases before this post.
The post's advice at `:26-28` — that driver authors can start adopting DRA with confidence — is the
rare forward-looking sentence in this archive that the pin simply confirms. The sentence at `:30`
that DRA is enabled by default is stronger now than when it was written: at 1.34 it was a default,
and from 1.35 the gate is locked, so it is not a choice at all.

**Broke.** Six links. The alias at `_index.md:7-8` keeps the one link without a fragment working and
cannot help the five with one, because an alias moves a reader to a page and the fragments now live
on three other pages in the same directory. A reader following the post's admin-access link today
lands on a section index that does not mention admin access.

**Never absorbed.** The label. Four blog posts write `resource.k8s.io/admin-access` and three
documentation pages write `resource.kubernetes.io/admin-access`, and the documentation includes the
reference that exists precisely to register label names. The post's one operational instruction —
the only sentence in it that tells a reader to change something in a cluster — is the sentence whose
central string the documentation tree does not agree with. *Do* settles which one a cluster takes,
which is a thing the pin cannot tell you.

**Overtaken by stasis.** *What's next?* asked for an equally ambitious 1.35 and got one new DRA
gate, the fewest of any release from 1.32 onward, and the features it had just announced as alpha
took two more releases rather than "the next couple of releases" to finish: one of the four is
stable at the pin, two are beta on by default, and one is beta and still off. Meanwhile
`DRASchedulerFilterTimeout`, shipped in the same release as the post, has been alpha for three
releases and has never been written about anywhere in the tree.

**The ladder**

`DynamicResourceAllocation.md` is a four-rung ladder, parsed from its frontmatter: alpha with
`defaultValue: false` from 1.30 to 1.31, beta with `defaultValue: false` from 1.32 to 1.33 — a beta
rung that was off, which is why the post can present "enabled by default" as news — then stable with
`defaultValue: true` and an explicit `locked: false` from 1.34 to 1.34, then stable with `locked:
true` from 1.35 and no `toVersion`. The body, three lines long, still describes the feature in terms
of "structured parameters", the phrase the 2022 design was renamed around.

Seven more gate files carry the features the post's two lists describe, and the split between the
lists is exactly the split between what the lab can run and what it cannot. On v1.35: the three beta
features are on without being asked for — `DRAAdminAccess` beta `true` from 1.34 to 1.35,
`DRAPrioritizedList` beta `true` from 1.34 to 1.35, `KubeletPodResourcesDynamicResources` beta
`true` from 1.34 to 1.35. The four alpha features are off — `DRAExtendedResource` alpha `false` from
1.34 to 1.35, `DRAConsumableCapacity` alpha `false` from 1.34 to 1.35, `DRADeviceBindingConditions`
alpha `false` from 1.34 to 1.35, `ResourceHealthStatus` alpha `false` from 1.31 to 1.35. Step 8
below exercises the first of the three that are on and step 9 the second; step 9 also shows what the
API server does with a field belonging to one that is off.

The eighth file is the one the exercise cannot use, and it is the one that explains the shape of
*Do*. `DRAOptionalNodeOperations` has a single rung, alpha `defaultValue: false` from 1.37, and the
pin is v1.37, so the feature that would let a ResourceSlice waive the kubelet handshake is exactly
as old as the pin and off in it. Without it a driver is not optional: a claim can be allocated by
the scheduler and still never reach a container, which is what steps 2 to 5 show and step 6 repairs.
The stall in step 5 is the finding, not a failure.

**Do**

1. Ask the cluster what it serves and what it already has. The first command is the sentence
   `:30-32` makes: which version of the group a client gets when it does not ask for one. The three
   listings should all be empty, which is the starting state the pin's tutorial also describes.

   ```sh
   kubectl version -o json | grep -m2 gitVersion
   kubectl create namespace bw-dra
   mkdir -p /tmp/bw-dra
   W=/path/to/kubernetes/website/content/en
   kubectl get --raw /apis/resource.k8s.io | python3 -c \
     'import json,sys; d=json.load(sys.stdin); print("preferred:", d["preferredVersion"]["version"]); print("served:   ", " ".join(v["version"] for v in d["versions"]))'
   kubectl get deviceclasses
   kubectl get resourceslices
   kubectl get resourceclaims -A
   NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
   echo "node: $NODE"
   ```

2. Be the driver. A ResourceSlice is the only thing a DRA driver has to publish for the scheduler to
   have something to allocate, and nothing stops an administrator publishing one by hand. Two
   devices, both with an `attributes` map and a `capacity` map, which is the combination
   `resource-slice-v1.md:241` says cannot exist.

   ```sh
   kubectl apply -f - <<YAML
   apiVersion: resource.k8s.io/v1
   kind: ResourceSlice
   metadata:
     name: bw-dra-pool-0
   spec:
     driver: blogwalk.example.com
     nodeName: $NODE
     pool:
       name: bw-dra-pool
       generation: 1
       resourceSliceCount: 1
     devices:
     - name: paper-0
       attributes:
         model:
           string: "quarto"
       capacity:
         memory:
           value: 64Gi
     - name: paper-1
       attributes:
         model:
           string: "octavo"
       capacity:
         memory:
           value: 8Gi
   YAML
   kubectl get resourceslices -o wide
   kubectl get resourceslice bw-dra-pool-0 -o jsonpath='{.spec.devices[0]}{"\n"}'
   ```

3. Create a DeviceClass over that driver and a ResourceClaim that selects on capacity, then read the
   claim's status while nothing is using it. The CEL expression is the pin's own shape from
   `dra-api.md`, with the driver name changed: capacities declared unqualified in the slice are
   addressed under the driver's domain in the selector.

   ```sh
   kubectl apply -f - <<'YAML'
   apiVersion: resource.k8s.io/v1
   kind: DeviceClass
   metadata:
     name: bw-paper
   spec:
     selectors:
     - cel:
         expression: device.driver == "blogwalk.example.com"
   ---
   apiVersion: resource.k8s.io/v1
   kind: ResourceClaim
   metadata:
     name: one-sheet
     namespace: bw-dra
   spec:
     devices:
       requests:
       - name: sheet
         exactly:
           deviceClassName: bw-paper
           selectors:
           - cel:
               expression: device.capacity["blogwalk.example.com"].memory.compareTo(quantity("10Gi")) >= 0
   YAML
   kubectl -n bw-dra get resourceclaim one-sheet -o jsonpath='status={.status}{"\n"}'
   ```

4. Give the claim a consumer. This is the step where the scheduler does the work the post is
   announcing: it picks a device that satisfies the selector, writes the allocation into the claim's
   status, reserves the claim for the Pod, and binds the Pod to the node.

   ```sh
   kubectl -n bw-dra apply -f - <<'YAML'
   apiVersion: v1
   kind: Pod
   metadata:
     name: claimer
   spec:
     containers:
     - name: c
       image: registry.k8s.io/e2e-test-images/agnhost:2.53
       command: ["sleep", "3600"]
       resources:
         claims:
         - name: sheet
     resourceClaims:
     - name: sheet
       resourceClaimName: one-sheet
   YAML
   sleep 20
   kubectl -n bw-dra get pod claimer -o jsonpath='node={.spec.nodeName} phase={.status.phase}{"\n"}'
   kubectl -n bw-dra get resourceclaim one-sheet \
     -o jsonpath='device={.status.allocation.devices.results[*].device} reservedFor={.status.reservedFor[*].name}{"\n"}'
   ```

5. Find out why the container is not running. The claim is allocated and the Pod is bound, and the
   kubelet is still waiting for a driver to prepare the device. The two directory listings are the
   missing half: `kubelet-files.md:143-144` names `plugins_registry` as where the kubelet looks for
   plugin sockets, and there is nothing in it.

   ```sh
   kubectl -n bw-dra describe pod claimer | sed -n '/^Events/,$p'
   kubectl -n bw-dra get pod claimer \
   ```

**Expect**

Step 1 prints two `gitVersion` strings, both `v1.35`, against a pin that is `v1.37`: everything
below is read at the pin and run two releases behind it. The discovery document answers the post's
`:30-32` directly — `preferred: v1`, which is the whole of the claim that the default API version is
now the stable one. The served list will also contain the betas the group still keeps; it should not
contain `v1alpha3`, because alpha groups need enabling by hand, and the page that tells you how is
`set-up-dra-cluster.md:40-57`, whose two lists of versions are indented differently from each other.
All three listings print `No resources found`, which is the same starting state the pin's tutorial
shows.

Step 2 accepts the ResourceSlice. `kubectl get resourceslices -o wide` prints one row whose DRIVER
is `blogwalk.example.com`, whose NODE is the node name, and whose POOL is `bw-dra-pool`, and the
last command prints a JSON object with `name`, an `attributes` map and a `capacity` map all set on
the same device. That object is the counter-example: `resource-slice-v1.md:241` says "Besides the
name, exactly one field must be set", the API server disagrees, and so does the pin's own sample at
`dra-features.md:267-279`, whose one device sets three fields besides its name.

Step 3 creates both objects and the claim's status is empty — either nothing printed at all or an
empty map, depending on whether the server stores a status stanza for an object that has none. What
matters is the absence of two keys: there is no `allocation` and no `reservedFor`. A ResourceClaim
is not allocated when it is created, even though a matching device has been published and the
selector would match it. Allocation is driven by a consumer, and there is not one yet.

Step 4 supplies one, and the two jsonpaths are the point of the exercise. The Pod's `spec.nodeName`
is set, so the scheduler bound it. The claim's status now reads `device=paper-0` and
`reservedFor=claimer`: `paper-0` and not `paper-1`, because the selector asks for at least 10Gi and
`paper-1` was published with 8Gi. The Pod's phase, though, is `Pending`. Everything the post
describes as the scheduler's job has happened, and the container has not started.

Step 5 says why. The events show the kubelet failing to prepare the claim's resources, and the
directory the kubelet watches for plugin sockets is empty or absent. The pin does not print the
event's reason string anywhere, so write down what your kubelet emits rather than matching it
against a string quoted here; the conditions are the checkable part, and they should read
`PodScheduled=True` with `Ready=False` and `ContainersReady=False`. The claim was allocated by a
component that needed nothing on the node, and it cannot be used by a component that needs something
on the node, which is the exact gap `DRAOptionalNodeOperations` exists to close and does not close
at v1.35.

Step 6 closes it the other way, by installing a driver. `rollout status` should report the DaemonSet
ready with one Pod, and `kubectl get resourceslices` should then show two rows: the one published by
hand in step 2, and a second whose driver is `gpu.example.com` and whose device list is `gpu-0`
through `gpu-8`, nine devices, the `NUM_DEVICES` the DaemonSet sets. If the rollout does not
complete, read the plugin's log before going on: the manifest names `dra-example-driver:v0.2.0` and
the pin's tutorial was written against v1.37, so a v1.35 kubelet is the one variable this exercise

Step 7 gets a container running on a claim. `pod0` reaches Ready, the claim's status names one of
the nine devices and a pool named after the node, and the Pod's log carries a `GPU_DEVICE_0=` line.
That line is the honest edge of the simulation: a real driver would have put a device node into the

Step 8 allocates the second subrequest. `pod1` reaches Ready, and the claim's status prints

matched something, and the pool has a device larger than a hundred terabytes, which would be worth

**Teardown**

Two namespaces and five cluster-scoped objects. The driver wrote a socket under
`/var/lib/kubelet/plugins_registry` and CDI files under `/var/run/cdi` on the node; deleting the
DaemonSet's namespace removes the Pod that owns them, and the last two commands check that nothing
is left behind. The checkout at the pin was only read.

```sh
kubectl delete namespace bw-dra dra-tutorial
kubectl delete deviceclass bw-paper bw-extended gpu.example.com
kubectl delete resourceslice bw-dra-pool-0
kubectl delete clusterrole dra-example-driver-role
kubectl delete clusterrolebinding dra-example-driver-role-binding
kubectl delete priorityclass dra-driver-high-priority
rm -rf /tmp/bw-dra
ssh zain@10.10.10.180 'sudo ls -A /var/lib/kubelet/plugins_registry /var/run/cdi 2>&1'
```

The ResourceSlice published by hand in step 2 has no owner and no controller, so nothing
garbage-collects it: it has to be deleted by name, and it will otherwise keep advertising two
devices that were never there. If a later exercise on this cluster finds a claim allocated to a
driver called `blogwalk.example.com`, this is why.
