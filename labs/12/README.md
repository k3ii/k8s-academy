# Labs — Phase 12, GitOps & platform engineering

Eighteen exercises in the order they are meant to run, for **the only phase that climbs up.** Eleven phases removed abstraction until `kubectl run nginx` was a cited path from terminal to syscall; this one builds abstraction back — deliberately, as a platform someone else could use. Its real deliverable is not the platform but [the critique of it](18-the-platform-and-its-critique.md): what your abstraction costs the developer who consumes it. Nothing here is new machinery — Flux is [the P4 reconcile loop](../../phases/04-controllers.md#m4-1), a Composition is a CRD with a controller, a vcluster is an apiserver-plus-syncer whose pods are real host pods. What is new is judgement.

**Every exercise is either a piece of the platform, or a measurement of what it costs.** The build-artifact files (delivery, golden path, KRO, Crossplane, the platform capstone) each produce a working piece a developer can drive; the rest measure the cost — a `kubectl top pod`, a `resources: {}` QoS class, a time-to-leak, a syncer's real RSS. This phase's citations are the **tools' own source** at pinned tags (helm-controller's drift mode, Crossplane's `mode` enum and empty `DeploymentRuntimeConfig`, the vcluster syncer), held to the same [archaeology standard](../../strands/source-archaeology.md#drills) as `k/k` — because platform tooling moves fast and a described mechanism is not a cited one.

Each file states one claim to test or one artifact to produce, links its [topology](../../strands/lab-topologies.md#platform) rather than restating a footprint, and ends with a teardown that deletes what it created and says whether the topology stays or goes. The framing — why each module exists, the question to answer from each tool's source — stays in [`phases/12-gitops-platform.md`](../../phases/12-gitops-platform.md). These files hold only what you type and what you should see.

## Order, topology, and the two groups — where the footprint fog patch resolves

This is [the heaviest phase in the curriculum](../../research/platform-engineering-footprints.md), and it is the second place the map warned a single 9.9GB window might not fit a whole phase. It resolves here, and the resolution is a **topology change plus a split**, not a softening.

**One node, added for this phase.** [`#14`](https://github.com/k3ii/k8s-academy/issues/14) costed the stack and found `pair` the wrong shape: nothing in P12 is a DaemonSet, so a second node would only pay the OS+kubelet tax twice and fragment 5GB into two buckets. The answer is [**`platform`**](../../strands/lab-topologies.md#platform) — one node, 6144MB / 4c / 40G, real untainted kubeadm — added *for P12* and **not a replay** of any earlier topology. It comes up at [exercise 1](01-gitops-the-reconcile-loop-you-already-wrote.md) and is destroyed by [the capstone](18-the-platform-and-its-critique.md).

**Two groups, with a teardown between — because both at once is unmeasured.** Per-exercise sequencing confirms the [research arithmetic](../../research/platform-engineering-footprints.md): against a ~1.0–1.3GB single-node baseline, **Group A** (delivery: exercises 1–9, ~1.9GB of requests, its heavy half being Istio + Prometheus at ~1.15GB) and **Group B** (platform API & tenancy: exercises 11–18, ~1.4GB) each sit near 2.5–3.2GB of the 6.0GB — enough headroom that observed RSS overshooting requests is survivable. Both co-resident would land near 3.9GB plus baseline; it probably fits, and it is still not done, because the one number the phase rests on — the vcluster syncer's real idle RSS — is unmeasured until [exercise 12](12-the-same-pod-in-two-apiservers.md) measures it. [**Exercise 10 is the boundary**](10-the-teardown-that-proves-git.md): it tears Group A's stack down (reclaiming the ~1.15GB) and doubles as the strongest GitOps test in the phase.

**Nothing in P12 was dropped for want of capacity, and nothing multi-cluster was added.** vcluster is the single-node answer to multi-tenancy precisely because [anything needing a second real cluster is out of scope](../../research/platform-engineering-footprints.md) — its syncer translates tenant pods into a host namespace, so "two views of one pod" is fully visible on one node. The one project that does not fit — [Backstage](08-backstage-read-never-installed.md) — is cut for its *build* (yarn tsc OOMs at ~4GB), not its runtime, and turns out to be the one whose mechanism payload was thinnest.

## The first lab step is a measurement

**[Exercise 1](01-gitops-the-reconcile-loop-you-already-wrote.md) opens with `kubectl top pod`** before anything is installed — the empty-node baseline every later install is measured against, and the number that makes the two-group budget real rather than assumed. **[Exercise 12](12-the-same-pod-in-two-apiservers.md) opens with `kubectl top pod -n vcluster-a`** — the single load-bearing measurement of the phase, because the two-tenant answer rests on the syncer's real RSS, not its 256Mi chart request (whose 4Gi default limit is a 16× tell that 256Mi is not the working set). If one tenant idles above ~600Mi, the exercise says to drop to one tenant plus a written walkthrough of the second.

## Sizing is an exercise, not a footnote

`resources: {}` is a live hazard on a single 6.0GB node, and the [build-track sizing standard](../../strands/build-mechanics.md#sizing) — memory request from measurement, memory limit a written-down decision — applies to the **platform components you install**, not only to your own artifacts. It lands as three exercises with observable outcomes: the [vcluster limit dropped 4Gi→1Gi](12-the-same-pod-in-two-apiservers.md), the [Crossplane function pod sized by a mandatory `DeploymentRuntimeConfig`](15-crossplane-the-two-lines-that-size-your-pod.md), and [12.C4](17-12c4-the-function-pod-with-no-limits.md), which removes that override and watches the mandatory pod run unbounded. The platform you build has the pod-sizing problem you spent [P8](../../phases/08-storage.md) learning to see.

## Exceptions and notes

- **Maturity is stated out loud, not badged.** [KRO has no CNCF tier](14-kro-custom-resource-in-children-out.md) (a SIG subproject, `v1alpha1`, its central CRD recently renamed), [vcluster is vendor OSS](12-the-same-pod-in-two-apiservers.md) (the chart's default image is the commercial build, so `loft-sh/vcluster-oss` is an explicit lab choice), and sealed-secrets is [absent from the landscape entirely](04-three-ways-to-not-commit-a-secret.md). The pattern is the lesson: platform tooling is markedly less mature than the layers below it.
- **Three stale levers to recognise, not try:** `mode: Resources` in a Crossplane Composition (removed from the schema, [exercise 15](15-crossplane-the-two-lines-that-size-your-pod.md)); "use k3s in the vcluster, it's lighter" (the distro is gone); "ESO requires an external secret store" (its `kubernetes` provider reads the local cluster, [exercise 4](04-three-ways-to-not-commit-a-secret.md)).
- **Two exercises need no cluster.** [Backstage](08-backstage-read-never-installed.md) is a source clone on [`forge`](../../strands/lab-topologies.md#build-guest); the [capstone critique](18-the-platform-and-its-critique.md) is a written document, though the platform it critiques must be running to critique honestly.
- **The word *understand* and the word *know* appear nowhere** — in this directory or the phase. The whole phase turns on the difference between driving a tool and being able to say what it costs, which those words paper over.
